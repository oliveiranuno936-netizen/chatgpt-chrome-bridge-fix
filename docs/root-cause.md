# 根因记录：为什么"重新安装 Browser 插件"永远修不好

本文记录本机实测到的**现象、环境事实与结论**，用于解释这套诊断/修复脚本为什么有效。
（为保证可公开发布，本文不含应用内部实现细节；脚本用法见 [../README.md](../README.md)。）

## 症状

在 ChatGPT 桌面版里让它操作 Chrome（例如"打开推特"），它会回答：

> Chrome 已安装，但 Codex 无法连接到 Chrome 的浏览器扩展桥接。
> 请在 ChatGPT/Codex 的「设置 → Computer use」中重新安装 Browser 插件，并确认 Chrome 扩展已启用。

而按提示去做（重装扩展、重装 Browser 插件、重启浏览器/应用）**永远不会成功**。

## 环境事实（实测）

| 项 | 实测结果 |
| --- | --- |
| 操作系统 | Windows 11 家庭中文版 25H2，build 26200 |
| 系统的文件加密能力 | `cipher /e` 返回 `The request is not supported.`；用户证书存储中没有加密文件系统证书 —— **家庭版不具备该能力** |
| 应用包形态 | ChatGPT 桌面版是 Microsoft Store 的 MSIX 包 |
| 包内文件属性 | 包内 `app` 目录带 `Encrypted` 标记（该目录下新增文件会被加密），包内 **5514 / 5514** 个文件均带该标记 |
| 对照组 | 同机其它 MSIX 包抽样文件**未**带该标记 —— 只有这一个包如此 |
| 复制实测 | 用系统复制命令、命令行复制、以及 Node 的文件复制 API，把包内文件复制到任意目标目录（C:、D:、E:、临时目录）**全部失败**：`The specified file could not be encrypted.`（Win32 `0x80071770`；在 Node 侧表现为 `UNKNOWN`，errno −4094） |
| 可行的替代方式 | 把文件内容**读出来再写入**（解密复制）可以成功 —— 即"读者能读，但复制会要求目标也被加密" |

## 失败链路（现象层）

1. 应用在**窗口获得焦点**以及**启动**时，都会执行一次"刷新内置插件市场"：
   把应用包里的插件目录复制到用户目录（`~/.codex/.tmp/bundled-marketplaces/...`）。
2. 这个复制会保留源文件的加密标记，因此要求**目标文件也能被加密**；本机的系统能力不支持 → **复制 100% 失败**。
3. 应用内部其实准备了"读出来再写"的降级复制路径，但它的触发条件与实际拿到的错误码不匹配，
   导致**降级从未生效**（全部日志中该降级事件出现 **0 次**，实测这条路径本身是可行的）。
4. 刷新失败 → 应用判定"内置插件不可用" → 浏览器相关插件被停用 →
   于是给出"无法连接到浏览器扩展桥接，请重新安装 Browser 插件"的回答。
   而重装走的是**同一条刷新路径**，同样失败 —— 这就是死循环的成因。
5. 该失败在本机日志中最早可追到 **2026-09-01**；2026-09-06、09-08 使用更早的应用版本时
   报的是同一个错误 → **不是某次更新引入的回归**，而是本机长期存在的环境性问题。

## 修复依据（原理层，不含实现细节）

应用在刷新之前会先检查：用户目录里是否存在与**当前版本、当前插件集合相匹配的缓存标记**。
若匹配，它就**直接复用现有副本**，完全不进入那次必然失败的复制。

本工具所做的，就是补齐让该缓存命中所需的两样东西：

1. **应用自己过滤后的插件清单**（应用会按当前平台与功能可用性过滤内置插件，本机为 7 个插件）；
2. **与该清单匹配的缓存标记文件**；
3. **与包内一致的插件文件内容**（应用还会抽查其中的技能文件内容是否与包内逐字节相同）。

由于本机的复制通道必然失败，第 3 项必须由修复脚本自己完成：**读出文件字节再写入**
（`fs.cp` / 系统复制会要求目标文件也能被加密，所以失败；读+写不会）。

修复脚本的流程：截获应用自己生成的清单 → 写入用户目录 → 重启应用并检查日志是否出现"复用"事件 →
若未命中则自动换一组参数重试 → 成功/失败都有明确输出（退出码 `0` / `1`）。

## 为什么应用更新后会复发

缓存标记里包含应用版本号、包标识与每个插件的版本号，另外还有一个与本机能力相关的开关字段；
标记是按**字符串全等**比较的，字段增删或取值变化都会失配。应用更新后这些值都会变化 → 标记失配 →
又回到那条必然失败的复制路径。**重新运行修复脚本即可**（脚本会重新截获清单、重算标记，
并把插件内容同步成新版本）。

除标记之外，应用还会校验运行目录里的插件内容（至少包含一个技能文件的内容哈希）——
所以应用更新后**只补标记是不够的**：插件文件也必须来自当前版本。v0.3.0 起修复脚本会一并同步。

标记的字段列表本身也会随构建变化（实测：`26.908.x` 有 `computerUseSkillVariant`，
`26.915.x` 增加了展示开关字段，`26.924.x` 又把 `computerUseSkillVariant` 删掉了）。
因此"未命中复用分支"时，正确做法是从应用的 JS bundle 里重新读出字段顺序，而不是猜。

另外，**应用更新还可能把扩展桥接一并清掉**（native host 清单文件与 Chrome 注册表项消失），
这时即使插件市场修好了也连不上；诊断脚本第 3 项会报出来，用 `repair-native-host.ps1` 重建即可。

## 另一条独立的失败链：电脑控制辅助服务随更新失效

桌面的「电脑控制」并不是走上面那条插件市场路径，它还需要一个本机服务来拉起辅助进程：
`CodexSandboxService.OpenAI.Codex`。这个服务的可执行文件**位于带版本号的 MSIX 包目录里**
（`...\WindowsApps\OpenAI.Codex_<版本>_x64__<hash>\app\resources\codex-windows-sandbox-service.exe`），
因此应用更新替换包目录后，正在运行或待启动的服务就会失败：
实测状态为 `Stopped`、退出码 `1067`（进程意外终止），而且 `StartMode` 虽是 `Auto` 也不会自己回来。

表现与插件问题完全不同：**浏览器桥接与插件市场都正常**，但让它操作浏览器时
「窗口清单为空」，读取浏览器状态报 `computer-use helper request failed`
（在对话里可能显示为 `nodeRepl.fetch request failed`）。

处理：`Start-Service CodexSandboxService.OpenAI.Codex` —— 普通用户权限即可（服务 ACL 允许启动）。
诊断脚本第 6 项会报出该服务未运行，修复脚本每次运行都会确保它处于运行状态。
需要注意的是，这种失效**每次应用更新后都可能复现**，而"崩溃自动重启"需要在管理员权限下配置
（`sc failure`），普通权限会被拒绝。

## 建议反馈给应用厂商的问题

1. 在**不具备文件加密能力**的系统（如 Windows 家庭版）上，MSIX 包文件仍带加密标记，
   导致应用自身的"刷新内置插件市场"复制必然失败；
2. 应用准备的"解密复制"降级路径未被触发（错误码判断不匹配），使问题表现为**永久性故障**；
3. 该失败被降级为"插件不可用"，并在回答里引导用户"重新安装浏览器插件"——而那一步同样会失败。
   建议把刷新失败明确暴露给用户，并给出可操作的信息。
